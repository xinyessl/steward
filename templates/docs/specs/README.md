# spec 生成规范（团队标准）

> 本文件是**给团队所有人（和 AI）看的 spec 编写标准**。新人照它写 spec 不踩坑；改动照它走保持一致。
> 一句话：**spec = PRD/需求 与 代码之间的「可验证契约」。无 spec 不开发；代码 / 测试 / commit 回链 spec ID。**

spec 的**第一读者是 AI**，同时服务两个场景：
- **迭代开发**：AI 读 spec → 在它基础上改系统（要"改哪、怎么算对、不臆造"）。
- **现场答疑**：现场 AI 读同一份 spec → 给实施同学答疑（要"这是什么、怎么配、为什么不对、怎么查"）。

---

## 一、说明书三层结构（先建立心智模型）

一个系统的说明书是**从外到内的三层漏斗**：

```
① 功能模块地图（总纲·docs/specs/00-功能模块地图.md）
     全部功能模块清单 + 每个模块要点 —— AI 进来先读它「定位」
   └─ ② 功能 spec（用户故事式，主体，可验收）—— 每个模块下 N 条
        └─ ③ 导读（type: guide）—— 只给「核心/复杂场景」的模块深讲机制
   ④ FAQ（docs/faq/）—— 常见问答（症状→定位→解法），随现场答疑沉淀
```

- **层1 功能模块地图**：最外层的口子，**求全覆盖、浅**（每模块一句话职责 + 链接）。
- **层2 主体 = 功能 spec**：一个"用户可感知的功能/页面" ≈ 一条 spec，带完整验收契约。
- **层2 深 = 导读**：**只给复杂模块**（如规则引擎、缓存机制）写一份 `type: guide` 的机制深讲；简单 CRUD 模块不必写。
- **层3 FAQ**：系统自身的常见问答，随答疑增量沉淀（外部实施 FAQ 另有其地，现场答疑时合并，不在这里维护）。

## 二、四种 spec，什么时候用哪个（`type` 字段）

| type | 是什么 | 什么时候用 | 模板 |
|---|---|---|---|
| `feature`（默认） | **可验收功能 spec**（用户故事+AC+DoD）| 每个用户可感知的功能一条；一条 ≈ 一个 PR ≈ 一次验收 | `_TEMPLATE.md` |
| `guide` | **系统导读**（域级机制/库表/数据流，参考基线）| 只给**核心/复杂/跨功能**的模块 | 无（照现有导读写，或直接用 md）|
| `process` | **流程 spec**（端到端跨模块流程的时序/状态机/排障）| 审方、开单、审批这类**流程性强**的系统的主流程 | `_TEMPLATE-流程.md` |
| （薄 spec）`feature` | **薄 spec**：已有导读打底、只做单次改动 | 在已有导读的系统上改一个功能/修一个 bug | `_TEMPLATE-薄spec.md` |

> `guide` 不走 dev/test/accept 流水线，看板里单列「📖 导读」。`feature`/`process` 是可验收单元。

## 三、怎么写一条功能 spec（用户故事式 · 8 节）

严格照 `_TEMPLATE.md` 的 8 节，每节要点：

1. **用户故事 / 目标**：`作为 <角色>，我要 <能力>，以便 <价值>`。角色/能力/价值都要具体，价值写清"为什么、解决什么"。
2. **范围**：包含 / 不包含（把边界划清，避免过度实现）。
3. **验收标准 AC**：`Given <前置> When <操作> Then <可观测结果>`，**每条可自动化判定**，用真实接口 + 真实列。修 bug 时把踩坑场景固化成一条 **AC-回归**。
4. **接口契约**：真实路径 / 入参 / 出参（来自当前 Controller，不编）。
5. **数据契约**：**真实表 / 列，逐列对真实库结构核过**（见铁律）；机制细节写"见导读 §x"交叉链接，不重复导读正文。
6. **业务规则 / 权限 / 留痕**：数据权限、按钮级权限、操作留痕、事务、幂等、并发锁。
7. **测试要点 + DoD**：怎么测（含连真库冒烟）+ 完成定义。
8. **NEEDS-HUMAN**：说不清的、库里查不到的、与预期不符的，一条条列出等人裁决。

> 已有导读的系统做单次改动，用**薄 spec**（`_TEMPLATE-薄spec.md`）：只写 §1 改动目标 + AC + 数据契约 + DoD，事实/库表**指回导读**，不重复。

## 四、铁律（不可违反）

1. **🚫 禁止臆造库表列名**：写数据契约/持久层前，**逐字段对照真实库结构**（`docs/db-schema.md` / mysqldump / 实体 `@TableName`·`@TableField` + mapper `resultMap`）。遗留命名常反直觉（某列叫 `user_code` 不叫 `account`）——**以真实结构为准；查不到对应表/列 → 标 `NEEDS-HUMAN` 停下，绝不假设**。
2. **spec-first**：需求/缺陷一律"先改 spec → 改测试 → 改码"。无 spec 不开发。
3. **一条 spec = 一个用户可感知功能 ≈ 一个 PR ≈ 一次验收**；别把整个模块写成一条，也别把一次改动散成多条。
4. **回链**：代码注释 / commit / PR 标题含 spec ID；测试用例名前缀 spec ID（如 `RE02_AC03_xxx`）。
5. **同步纪律 + 现状快照**：行为/规则/字段变了 → **就地改**对应 spec/导读的 AC/章节改成最新态（spec 是"现状快照"不是"变更日志"，**禁止在 spec 里堆 `增补(日期)/校正(日期)` 流水块**）；纯 bug/重构不改 spec，变更历史只进 `docs/changes/CHG-*.md`。
6. **测试不只 mock**：有真实库的项目，每条 spec 至少补一条**连真库冒烟**（或注明已对真实库结构核过字段映射）。
7. **🩹 单条 spec 有体量红线（防膨胀）**：**~800 行 / ~40KB / AC>20**（阈值可调；`type: guide` 导读放机制全景，不受此限）。
   - **生成时就守住，别先堆成大块再拆**：写一条功能 spec 前先估体量，**预判会超红线 → 一开始就设计成「导读（机制）+ 多条 feature spec（每条一个子功能）」分开写**。一条 feature spec 只覆盖一个用户可感知功能，天然就在红线内。
   - **已超的就地拆**：改动时发现某条已过红线 → 停下拆：抽机制成 `导读`（`type: guide`）+ 按子功能拆多条 feature spec（各新 ID）+ 回写总纲；新长出的相对独立子功能 = **新建 spec，不塞老 spec**。
   - 根因是"改一次就往尾部追加一段"（DC-14 十几个"增补(日期)"块摞成 62K），所以必须配合铁律 5「就地改·禁流水块」一起守，否则 spec 隔阵子又膨胀成怪物、又得整体梳理。

## 五、命名 / ID / status / DoD

- **文件名**：`<模块前缀>-<序号>-<名称>.md`，如 `RE-02-规则图画布编辑与审核.md`（RE=规则引擎、DM=资料、DICT=字典…前缀本项目统一）。导读用 `<域>-00-xx导读.md`。
- **ID 全局唯一**（如 `RE-02`），写在 frontmatter `id:`。
- **frontmatter 必填**：`id / title / module / type / status`；建议补 `source / guide / priority / depends_on`。
- **status 生命周期**：`draft（草拟）→ ready（评审通过可开发）→ in-dev → testing → accepted（人验收通过）`。逆向扫已上线代码标 `accepted`（as-built 基线）。
- **DoD 统一门槛**：① 所有 AC（含回归）自动化通过 ② 接口契约校验通过 ③ 连真库冒烟通过 ④ 无臆造字段 ⑤ 行为有变已回写 spec/导读 ⑥ 人类验收。

## 六、给一个模块 / 一个项目铺开（可并行 · 增量）

以**功能模块地图为清单**，一个模块一个模块填满，每个模块固定 5 步：

1. **总纲登记**（层1）：`00-功能模块地图.md` 里补该模块行（职责 + 导读要点 + 功能 spec 清单 + FAQ）。未做标「待生成」。
2. **产功能 spec**（层2 主体）：读该模块**当前代码** + 真实库结构 → 每个功能一条用户故事式 spec（见第三节）。
3. **导读**（层2 深，仅复杂模块）：有跨功能复杂机制才写 `type: guide`；功能 spec 交叉链接它。
4. **起 FAQ 骨架**（层3）：`docs/faq/<模块>.md`，随答疑沉淀。
5. **回填总纲 + 跑 `node tools/board.mjs`**。

**三条原则**：① 一次一模块、跨模块可并行（各写各的文件不冲突，同模块内串行）；② **增量不重做**（已有的不动，只补总纲里"待生成"的）；③ **锚定真实库**（数据契约永远对真实结构，这是防臆造的地基）。

> 存量项目铺这套 = **叠加**，不是重来：旧的细 spec 原样留作层2，只新增「总纲（从现有 module 汇总）+ FAQ 骨架」。

## 七、模板与工具

- **模板**（本目录）：`_TEMPLATE.md`（功能 spec）· `_TEMPLATE-薄spec.md`（薄改动）· `_TEMPLATE-流程.md`（流程 spec）· `00-功能模块地图.md`（层1）；FAQ 模板在 `docs/faq/`。
- **命令**：`/scan`（逆向产出三层说明书）· `/spec`（需求转 spec，先拆条+影响面）· `/build`（按 spec 实现+测试+真库冒烟）· `/fix`（缺陷闭环）· `/accept`（验收）。
- **看板**：`node tools/board.mjs` 从 spec 头部 `status` + `type` 派生 `docs/board.json`（控制台读它，识别 `type: guide` 单列）。**不要手改 board。**

---

> 变更（上线后）：新建 `docs/changes/CHG-*.md` 关联受影响 spec，走「改 spec → 改测试 → 改码 → 回归 → 验收」。踩过的非显然坑 → 沉淀进 `docs/lessons.md`（本项目）或全局经验库。
