# 完善本项目 spec —— AI 作业指导（把本文件交给 AI，让它照做）

> **使用方式**：把本文件连同"请按它完善本项目的 spec"一起发给你的 AI（Claude / Codex 等，需能读本项目代码）。
> **AI 你好**：你要以本文件为准，读本项目的**真实代码 + 真实库结构**，把 `docs/specs/` 的规约补全、纠错、规范化。**最重要的一条：禁止臆造**——说不清、库里查不到的，一律标 `NEEDS-HUMAN` 停下问人，绝不编造。

---

## 一、你的任务（一句话）

完善本项目的 spec：① 现有 spec 逐条**体检纠错/补全** ② 代码里有、却没 spec 的功能**补新的** ③ 建/补**功能模块地图（总纲）+ FAQ 骨架**。全程锚定真实代码与真实库。

spec 的第一读者是 AI，服务两个场景：**迭代开发**（改哪、怎么算对、不臆造）和**现场答疑**（这是什么、怎么配、为什么不对、怎么查）。两个都要照顾到。

---

## 二、动手前必做：摸清现状

1. **盘点** `docs/specs/`：现有哪些 spec、各自 `id / module / title / status`、结构齐不齐、内容对不对。
2. **找真实库结构**（数据契约的**唯一权威来源**，按项目里存在的用，优先级从高到低）：
   - `docs/db-schema.md` / mysqldump 导出 / `*.sql` 建表脚本；
   - 都没有 → 读**实体类**（`@TableName` / `@TableField`）+ **mapper XML**（`resultMap` + SQL 里的真实表/列）；
   - **若项目连着可访问的真实库、且你有条件**：只读导出一份真实表结构最靠谱（表/列/类型/注释）；
   - 实在找不到对应表/列 → **标 `NEEDS-HUMAN`，绝不假设**。
3. **通读入口 / 路由 / 菜单**，归纳出**功能模块清单**（产品面，几个大块；别按 `xxx-server`/`xxx-web` 代码目录硬分）。

---

## 三、目标产出：三层说明书

```
① 功能模块地图（总纲 · docs/specs/00-功能模块地图.md）
     全部功能模块清单 + 每个模块要点 —— AI 进来先读它「定位」
   └─ ② 功能 spec（用户故事式，主体，可验收）—— 每个模块下 N 条
        └─ ③ 导读（type: guide）—— 只给「核心/复杂」模块深讲机制（简单模块不必写）
   ④ FAQ（docs/faq/<模块>.md）—— 常见问答（症状→定位→解法）
```

- **层1 功能模块地图**：求全覆盖、浅（每模块一句话职责 + 链接）。
- **层2 功能 spec**：一个"用户可感知的功能/页面" ≈ 一条 spec，带完整验收契约（下面第四节）。
- **层2 导读**：**只给复杂/跨功能机制**的模块写一份 `type: guide`；功能 spec 的机制"就地摘要 + 复杂链路交叉链接导读"。
- **层3 FAQ**：系统自身常见问答，先起骨架。

## 四、一条功能 spec 的标准格式（照抄这 8 节）

```markdown
---
id: <模块前缀-序号，如 RE-02>
title: <功能名>
module: <所属功能模块>
type: feature
source: 逆向(真实库校对)
guide: <关联导读路径，无则删>
priority: P0 | P1 | P2
status: draft
owner_human:
depends_on: []
---

## 1. 用户故事 / 目标
作为 <角色>，我要 <能力>，以便 <价值>。   ← 角色/能力/价值都具体，价值写清"为什么"

## 2. 范围
- 包含：… / 不包含：…

## 3. 验收标准（AC · Given-When-Then · 每条可自动化判定）
- **AC1** Given <前置> When <操作/接口> Then <可观测结果，用真实字段>
- **AC-回归** <若修 bug：把踩坑场景固化成一条>

## 4. 接口契约
| 方法 | 路径（当前 Controller 真实的） | 入参 | 出参 |

## 5. 数据契约（真实表/列，逐列对真实库结构核过，禁臆造）
| 表 | 列 | 用途 | 出处 |
> 需要新表/改列 → 停，标 NEEDS-HUMAN。

## 6. 业务规则 / 权限 / 留痕
（数据权限、按钮级权限、操作留痕、事务、幂等、并发锁）

## 7. 测试要点 + DoD
（怎么测 + 连真库冒烟 + 完成定义）

## 8. NEEDS-HUMAN
（说不清的、库里查不到的、与预期不符的，逐条列出）
```

> 已有导读打底、只做**单次改动**时，可用"薄 spec"：只写 §1 改动目标 + AC + 数据契约 + DoD，事实/库表指回导读。

---

## 五、铁律（违反 = 返工）

1. **🚫 禁止臆造库表列名**：写数据契约前**逐字段对照真实库结构**。遗留命名常反直觉（列可能叫 `user_code` 不叫 `account`）——以真实结构为准；查不到 → `NEEDS-HUMAN`，别假设。
2. **以代码/库为准**：spec 写"现状"，只写代码能确证的；项目里的 PRD/旧文档可能过时，仅参考，与代码冲突以代码为准。
3. **一条 spec = 一个用户可感知功能** ≈ 一个 PR ≈ 一次验收；别把整个模块写成一条。
4. **纠错不删原文**：发现旧 spec/导读的表名或描述与真实库不符 → **不要擅自删改正文**，而是**标出来（在该处或 §8 记 NEEDS-HUMAN）交人确认**。
5. **测试不只 mock**：有真实库的项目，每条 spec 至少补一条**连真库冒烟**思路（或注明已对真实结构核过字段映射）。

---

## 六、具体动作（逐条走）

### A. 现有 spec 逐条体检
对每条现有 spec，核对并修（改不动的标 NEEDS-HUMAN）：
- [ ] 有 §1 **用户故事**（作为…我要…以便…）吗？没有 → 补。
- [ ] **AC** 是 Given-When-Then、可自动判定、用真实接口/列吗？模糊/主观的 → 改具体。
- [ ] **数据契约**的表/列在**真实库里存在**吗？**逐列核**；对不上 → 纠正或标 NEEDS-HUMAN（不删原文）。
- [ ] **接口路径**是当前 Controller 真实的吗？
- [ ] 结构齐 8 节吗？缺的补。

### B. 缺的功能补 spec
代码里有、却没 spec 的功能 → 按第四节新建一条。

### C. 建/补总纲 + FAQ
- `docs/specs/00-功能模块地图.md`：每个功能模块一行（一句话职责 + 该模块的功能 spec 清单 + FAQ 链接）；求全覆盖。
- `docs/faq/<模块>.md`：把代码里**显见的报错路径 / 配置开关 / 易错点**先落几条（症状→去哪看→怎么解），之后随答疑沉淀。

---

## 七、规矩：一次一模块、增量、可并行

- **一次聚焦一个模块**；不同模块各写各的文件、互不冲突（可并行）；同模块内串行。
- **增量、不重做**：已有且没问题的 spec 别动，只补/纠有问题的和缺的。
- **锚定真实库**：数据契约永远对真实结构——这是防臆造的地基。

---

## 八、干完给人一份报告

1. 改了 / 建了哪些 spec（id + 一句话）；
2. 每条数据契约命中了哪些**真实表**；
3. 发现的**代码 / 真实库 / 旧 spec 三者不符之处**（列出来交人核对，**未擅自删原文**）；
4. 所有 `NEEDS-HUMAN`（说不清、库里查不到、与预期不符的）。

> 记住：**你产出的是"以真实代码+真实库为准、可被人核对"的 spec，不是听起来合理但可能编造的文档。** 拿不准就停下标 NEEDS-HUMAN。
